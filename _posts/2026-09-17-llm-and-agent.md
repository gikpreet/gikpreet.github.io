LLM(Large Language Model)과 AI Agent는 생성형 AI를 이해하는데 핵심적인 두 개념입니다. 두 기술은 매우 밀접하게 연결되어 있지만, 같은 의미로 사용해서는 안됩니다. LLM은 언어를 이해하고 생성하는 모델이고, AI Agent는 그런 모델을 중심으로 여러 도구와 실행 기능을 결합하여 실제 목표를 수행하는 시스템입니다.

이 둘의 차이를 가장 간단하게 표현하면 아래와 같습니다.

> LLM은 생각하고 생성하는 모델이며, AI Agent는 판단하고 행동하는 시스템입니다.
{: .prompt-info }

이 차이는 단순히 기능의 많고 적음을 의미하지 않습니다. LLM과 AI Agent의 차이는 인공지능이 사용자와 싱호작용하는 방식, 외부 환경을 다루는 방식, 그리고 실제 작업을 수행하는 방식이 어떻게 달라지는지를 보여주는 중요한 기준입니다.

## LLM은 언어를 중심으로 작동

LLM은 일반적으로 대규모 언어 모델이라고 번역합니다. GPU, Claude, Gemini와 같은 모델이 대표적인 예입니다. 이런 모델은 방대한 양의 텍스트와 다양한 형태의 데이터를 학습하여 사용자가 입력한 문장을 해석하고, 현재 제공된 문맥에 적합한 결과를 생성합니다.

가장 단순하게 표현하면 LLM의 구조는 다음과 같습니다.

```
      입력 
       │ 
       ▼ 
┌──────────────┐
│     LLM      │ 
└──────────────┘
       │ 
       ▼ 
      출력
```

사용자가 "Java에서 ArrayList와 LinkedList의 차이를 설명해 주세요"라고 질문하면 LLM은 두 자료구조의 내부 구조와 성능 차이, 적합한 사용 사례를 설명할 수 있습니다. "LinkedList를 Java로 구현해 주세요"라고 요청하면 소스 코드를 생성할 수도 있습니다.

이처럼 LLM은 설명, 요약, 번역, 분석, 코드 생성, 문서 작성 등 매우 다양한 작업을 수행할 수 있습니다. 그러나 여기에서 중요한 점은 LLM의 기본적인 역할이 여전히 정보를 생성하는 것이라는 사실입니다.

예를 들어 사용자가 다음과 같은 요청을 LLM에 한다면,

> 이 Java 프로젝트의 오류를 수정해 주세요

LLM이 프로젝트의 소스 코드와 오류 메시지를 전달 받는다면 수정 방법을 설명하거나 수정된 코드를 알려줄 수 있습니다. 하지만 LLM이 사용자의 컴퓨터에 있는 프로젝트 파일을 직접 열어 수정하지는 않습니다. 테스트 명령을 실행하거나, 결과를 확인하고 실패했을 때 추가 수정까지 이어가지도 않습니다.

LLM은 **무엇을 해야 하는지 설명할 수는 있지만, 실제 환경에서 그 일을 수행하는 것은 별도의 문제입**니다.

## LLM은 주어진 Context에서 작동

LLM을 이해하려면 Context라는 개념을 이해해야 합니다. LLM은 기본적으로 자신에게 전달된 정보 내에서 현재 상황을 판단합니다.

여기에는 사용자의 질문, 이전 대화 내용, 제공된 문서, 첨부된 코드, 현재 작업에 필요한 정보등이 포함될 수 있습니다.

```
현재 질문/이전 대화/제공된 문서/첨부 코드/현재 작업 정보

                      │
                      ▼ 
                     LLM 
                      │ 
                      ▼ 

                   응답 생성
```

LLM은 사용자의 컴퓨터에 존재하는 모든 파일을 자동으로 알지는 못합니다. 현재 실행 중인 애플리케이션의 상태를 직접 확인하는 것도 아니며, 데이터베이스 내부의 데이터를 자동으로 읽을 수도 없습니다.

사용자가 "내 컴퓨터에서 Student.java 파일에 오류가 있는지 확인해 주세요"라고 요청해도, LLM 자체에는 그 파일을 직접 읽을 수 있는 능력이 없습니다. 파일 내용을 사용자가 제공하거나, 파일 시스템과 연결된 별도의 도구가 있어야 실제 내용을 확인할 수 있습니다.

"테스트를 실행해서 오류의 원인을 찾아 주세요" 같은 요청에 대해서도 마찬가지입니다. LLM은 `mvn test`나 `gradle test`와 같은 명령을 알려줄 수는 있지만, 실제 터미널을 사용할 수 없다면 테스트를 실행할 수는 없습니다.

이런 점에서 LLM의 구조는 명확합니다.

> 입력 -> 추론 -> 출력
{: .prompt-tip }

출력은 설명, 코드, 요약, 분석, 계획과 같은 정보의 형태로 나타납니다.

## AI Agent: 목표 수행을 위한 시스템

AI Agent는 LLM 보다 더 넓은 개념입니다. 현대적 AI Agent는 보통 LLM을 핵심 추론 엔진으로 사용하면서, 여기에 메모리, 도구, 계획 기능, 실행 환경 등을 결합합니다. 이를 구조적으로 표현하면 아래와 같습니다.

```
                AI AGENT 
                   │ 
  ┌────────────────┼────────────────┐ 
  │                │                │
  ▼                ▼                ▼ 
 LLM             Memory           Tools
  │                │                │ 
  └────────────────┼────────────────┘
                   │
                   ▼
                Planning
                   │
                   ▼
                Execution
                   │ 
                   ▼ 
               Observation
```

LLM이 현재 상황을 이해하고 무엇을 해야 하는지 판단한다면, Tools는 실제 행동을 수행합니다. Memory는 과거의 정보나 프로젝트 상태를 저장하며, Planning은 목표를 여러 개의 세부 작업으로 나눕니다. Execution은 계획한 작업을 실제로 실행하고, Observation은 그 결과를 다시 확인합니다.

AI Agent는 단순히 답변을 생성하는 시스템이라기 보다, 외부 환경과 상호작용하면서 목표를 달성하는 시스템으로 이해하는 것이 좋습니다.

## Prompt와 Goal

LLM과 AI Agent를 구분할 때 중요한 차이 중 하나는 사용자가 무엇을 전달하느냐에 있습니다.

LLM에는 보통 Prompt라고 부르는 질문이나 지시를 전달합니다. 예를 들어 다음과 같습니다:

> "ASP.NET Core에서 PostgreSQL에 연결하는 방법을 알려주세요."

이런 요청에 대해 LLM은 필요한 연결 파일, 라이브러리, 연결 문자열, 예제 코드등을 설명합니다. 

반면 AI Agent에서는 Prompt가 아닌 Goal, 즉 목표를 설정합니다.

> "지정한 ASP.NET Core 프로젝트에서 지정한 PostgreSQL에 연결되도록 수정해주세요"

LLM에서는 설명을 요구하지만, AI Agent에서는 실제 프로젝트의 상태 변경을 요구합니다. Agent는 이 목표를 달성하기 위해 다음과 같은 작업을 스스로 구성할 수 있습니다. 사용자가 모든 단계를 직접 지정하지 않아도 Agent가 목표를 해석하고 필요한 작업을 나누어 처리할 수 있습니다.

```
프로젝트 구조 확인
      ↓
라이브러리 확인
      ↓
설정 파일 확인
      ↓
DB 연결 정보 확인
      ↓
코드 수정
      ↓
애플리케이션 실행
      ↓
연결 테스트
      ↓
문제가 있으면 다시 수정
```

이 과정을 **Task Decomposition**, 즉 작업 분해라고 합니다.

## LLM은 응답을 생성, Agent는 반복

LLM의 기본적인 상호 작용은 비교적 단순합니다. 아래와 같이 입력에 대해 출력을 생성하는 구조입니다.

> INPUT → LLM → OUTPUT
{: .prompt-info }


AI Agent는 하나의 목표를 달성하기 위해 여러 차례 판단하고 행동합니다.

```
GOAL
 ↓
THINK
 ↓ 
ACT
 ↓ 
OBSERVE
 ↓ 
EVALUATE
 ↓ 
THINK
 ↓ 
ACT
```

이런 구조를 일반적으로 Agent Loop라고 부릅니다. 

Agent가 ASP.NET Core 프로젝트의 오류를 수정한다고 할 때, Agent는 먼저 테스트를 수행할 수 있습니다. 테스트 겨로가 오류가 발생하면, 오류 결과를 새로운 입력으로 받아들입니다. 그리고 해당 오류를 확인하고, 파일을 읽고, 관련 객체가 어디서 생성되는지 검색하고, 문제의 원인을 분석합니다. 그 다음 코들ㄹ 수정하고 다시 테스트를 실행합니다. 테스트가 또 실패하면 새로운 오류를 분석하고 다시 수정합니다.

다음과 같은 순환 구조가 형성됩니다.

```
    THINK
      │ 
      ▼ 
     ACT
      │ 
      ▼ 
    OBSERVE
      │ 
      ▼ 
    EVALUATE
      │ 
   목표 달성? 
    /    \ 
   Yes    No
    │      │ 
    ▼      └────→ THINK 
 COMPLETE
```

이처럼 Agent는 실행 결과를 다음 판단의 입력으로 다시 사용합니다. 이 반복적인 구조가 바로 Agent의 중요한 특징입니다.

## AI Agent에서 LLM

AI Agent 내부에서도 LLM은 매우 중요한 역할을 합니다. 다만 LLM 자체가 Agent 전체를 의미하는 것은 아닙니다.

Agent 안에서 LLM은 주로 현재 상황을 이해하고, 다음 행동을 판단하고, 사용할 도구를 선택하며, 실행 결과를 해석하는 역할을 담당합니다. Agent 시스템에서는 LLM을 **Resoning Engine**, 즉 추론 엔진으로 볼 수 있습니다.

예를 들어, Agent가 다음과 같은 도구를 사용할 수 있다고 해 봅시다.

```
read_file()
write_file()
search_file()
run_terminal()
web_search()
database_query()
git()
```

사용자가 “이 프로젝트가 왜 빌드되지 않는지 확인하고 수정해 주세요”라고 요청하면 Agent 내부의 LLM은 먼저 어떤 도구를 사용해야 하는지 판단합니다.

우선 `run_terminal()`을 사용해 빌드를 실행할 수 있습니다. 빌드가 실패하면 오류 메시지를 해석하고, `search_file()`이나 `read_file()`을 이용해 관련 소스 코드를 확인합니다. 필요한 경우 파일을 수정한 뒤 다시 빌드를 실행합니다. 여기서 중요한 점은 LLM이 직접 파일 시스템이나 터미널이 되는 것은 아니라는 사실입니다.

LLM은 무엇을 언제 사용해야 하는지 판단하고, Tool은 실제 행동을 수행합니다.

## Tool과 Agent

Tool은 Agent에게 행동할 수 있는 능력을 제공합니다. AI Agent의 실제 능력은 어떤 Tool과 연결되어 있는지에 따라 크게 달라집니다. 같은 LLM을 사용하더라도 사용할 수 있는 도구가 다르면 수행할 수 있는 작업도 달라집니다.

> Knowledge ≠ Capability
{: .prompt-warning }

즉, 어떤 작업의 방법을 알고 있다고 해서 반드시 그 작업을 실제로 수행할 수 있는 것은 아닙니다.

LLM이 Git 사용법을 알고 있다고 하더라도 Git 도구와 저장소 접근 권한이 없다면 실제 commit이나 push를 수행할 수 없습니다. 반면 Agent가 Git 도구와 적절한 권한을 가지고 있다면 그 지식을 실제 행동으로 연결할 수 있습니다.

## Context와 Memory

LLM과 Agent의 차이를 이해할 때 Context와 Memory의 차이도 중요합니다.

Context는 현재 작업을 수행하는 데 필요한 정보입니다. 현재 질문, 현재 파일, 최근 오류 메시지, 프로젝트 구조 등이 이에 해당합니다. 반면 Memory는 이후에도 다시 사용할 수 있도록 저장된 정보입니다.

예를 들어 장기적으로 특정 프로젝트를 관리하는 Agent라면 다음과 같은 정보를 기억할 수 있습니다.

```
PROJECT MEMORY

Project      : student-management
Language     : Java
Build Tool   : Gradle
Database     : PostgreSQL

Progress
├─ Student 클래스 구현 완료
├─ Repository 구현 완료
└─ Service 테스트 진행 중

Next Task
└─ Transaction 예제 작성
```

이를 간단히 표현하면 다음과 같습니다.

> Context = 지금 작업에 필요한 정보
> Memory  = 이후에도 다시 사용할 정보

LLM은 주로 현재 Context를 바탕으로 작동하지만, Agent는 별도의 Memory 시스템을 통해 장기적인 작업의 연속성을 유지할 수 있습니다.

특히 Personal Agent나 장기간 프로젝트를 관리하는 Agent에서는 Memory가 매우 중요한 역할을 합니다.

## LLM은 정보를 생성, Agent는 상태를 변화

LLM과 AI Agent의 차이를 좀 더 본질적으로 살펴보면 **정보 생성과 상태 변화**의 차이로 설명할 수 있습니다. 

LLM이 주로 생성하는 것은 설명, 분석, 코드, 요약, 계획, 문서와 같은 정보입니다. 반면 AI Agent는 외부 환경의 실제 상태를 변화시킬 수 있습니다.

예를 들어, 아래와 같은 코드가 Hello.cs 파일로 있다고 있다고 할 때,

```cs
public class Hello {
    public static void Main(string[] args) {
        System.out.println("Hello, World!");
    }
}
```

오류를 찾아 수정하라고 하면 LLM은 파일을 직접 열지 못합니다. 프롬프트에 코드를 복사해서 붙여넣으면, 아래와 같은 결과를 보여줍니다.

```
System.out.println은 Java 문법이며, C#에서는 System.Console.WriteLine을 사용해야 합니다.

수정된 올바른 C# 코드는 다음과 같습니다.

C#
public class Hello {
    public static void Main(string[] args) {
        System.Console.WriteLine("Hello, World!");
    }
}
상단에 using System;을 추가하면 더 간결하게 작성할 수도 있습니다.

C#
using System;

public class Hello {
    public static void Main(string[] args) {
        Console.WriteLine("Hello, World!");
    }
}
```

AI Agent는 해당 파일을 열어서 직접 수정할 수 있습니다. AI Agent는 (권한을 부여했다면) 해당 파일을 직접 열어 수정하고 저장합니다.

```cs
using System;

public class Hello {
    public static void Main(string[] args) {
        Console.WriteLine("Hello, World!");
    }
}
```

즉, LLM은 주로 정보를 생성하는 반면, Agent는 Tool을 사용해 외부 시스템의 상태를 실제로 변경할 수 있습니다.

물론 모든 Agent가 항상 상태를 변경하는 것은 아닙니다. Research Agent와 같이 읽기와 분석만 수행하는 Agent도 존재합니다. 중요한 점은 Agent가 필요할 경우 외부 환경과 상호작용할 수 있도록 설계된 시스템이라는 것입니다.

## Agent가 항상 더 지능적인 것은 아니다

AI Agent가 이름때문에 LLM보다 더 높은 수준의 인공지능이라고 생각하기 쉽지만, 항상 그런것은 아닙니다.

두 시스템이 동일한 LLM을 사용할 수도 있습니다. 이럴 때, AI Agent가 어떤 구성을 가지고 있는지에 따라 능력이 좌우됩니다.

A 시스템은 아래와 같이 구성되어 있고,

```
 LLM
  │ 
  ▼ 
Answer
```

B 시스템의 구성은 아래와 같다고 하면,

```
         LLM
          │ 
   ┌──────┼──────┐
   ▼      ▼      ▼ 
 Memory Tools Planning
   │      │      │
   └──────┼──────┘
          ▼
       Execution
```

B 시스템은 Memory, Tools, Planning, Execution 기능을 추가로 가지고 있으므로 훨씬 복잡한 작업을 수행할 수 있습니다. 따라서 Agent의 능력을 평가할 때는 어떤 모델을 사용하는지만 보아서는 안됩니다. 다음과 같은 요소를 함께 고려해야 합니다.

* Model 
* Tools 
* Memory 
* Planning 
* Execution 
* Environment 
* Permissions 
* Feedback Loop

## AI Agent에서 권한 관리의 중요성

LLM은 일반적으로 정보를 생성하는데 그치기 때문에 잘못된 답변이 나오더라도 사용자가 그것을 무시하거나 수정할 수 있습니다. 하지만 AI Agent는 실제 행동을 수행할 수 있기 때문에 잘못된 판단의 영향이 훨씬 커질 수 있습니다. 

AI Agent는 아래와 같은 권한들을 가질 수 있습니다.

* 파일 읽기
* 파일 수정 
* 파일 삭제 
* Git commit 
* Git push 
* Database update 
* 서버 배포 
* 이메일 발송

이런 경우, Agent가 잘못 판단하여 동작하게 되면 실제 파일 삭제, 잘못된 배포, 엉뚱한 이메일 발송, 데이터 변경 등과 같은 잘못된 결과로 이어질 수 있습니다. 그래서 AI Agent 시스템에서는 **Human-in-loop**, 즉 사람이 중요한 단계에서 확인하거나 승인하는 구조가 매우 중요합니다. 위험도가 낮은 작업은 자동으로 실행하고, 중요한 작업은 사용자 승인을 요구하도록 설정하는 것이 좋습니다. 예를 들면 다음과 같습니다.

|작업|권한|
|---|----|
|파일 읽기|자동 실행|
|코드 검색|자동 실행|
|테스트 실행|자동 실행|
|파일 수정|허용|
|Git commit|사용자 확인|
|Git push|사용자 확인|
|데이터 삭제|사용자 확인|
|운영 서버 배포|사용자 확인|

좋은 Agent는 무조건 많은 권한을 가진 Agent가 아닙니다. 어떤 작업을 자동화하고, 어떤 작업에서 사용자의 승인을 받아야 하는지를 적절하게 구분할 수 있는 Agent가 더 안정적이고 실용적입니다.

## LLM과 AI Agent의 관계

지금까지의 내용을 하나의 구조로 정리하면 다음과 같습니다.

```
          LLM 
           │ 
     추론과 생성 담당
           │ 
           ▼ 
  ┌─────────────────┐
  │     AI Agent    │
  └─────────────────┘
           │
  ┌────────┼────────┐ 
  ▼        ▼        ▼ 
Tools    Memory   Planning
  │        │        │
  └────────┼────────┘ 
           ▼ 
        Action
           │ 
           ▼
      Observation 
           │ 
           ▼
         Result
```

LLM은 Agent의 핵심 구성 요소 일 수 있지만 Agent 전체는 아닙니다. 비유하자면 LLM은 자동차의 엔진과 비슷하고, AI Agent는 엔진과 바퀴, 조향 장치, 센서, 브레이크, 제어 장치까지 포함한 완성된 자동차에 가깝습니다. 엔진은 자동차에서 매우 중요한 요소이지만 엔진 하나만으로 목적지까지 이동할 수는 없습니다. 엔진의 힘을 실제 움직임으로 바꾸려면 여러 구성 요소가 함께 작동해야 합니다.

AI Agent도 마찬가지입니다. LLM의 추론 능력을 실제 행동으로 연결하려면 Tools, Memory, Planning, Execution과 같은 요소가 필요합니다.

## 명령에서 질문으로, 그리고 목표로

LLM과 AI Agent의 차이는 컴퓨터를 사용하는 방식의 변화와도 연결됩니다.

전통적인 소프트웨어에서는 사용자가 컴퓨터에게 구체적인 명령을 입력해야 했습니다.

> COMMAND
{: .prompt-info }

LLM이 등장하면서 사용자는 자연어로 질문하고 요청할 수 있게 되었습니다.

> PROMPT
{: .prompt-info }

AI Agent는 여기에서 한 단계 더 나아갑니다. 사용자는 상세한 절차보다 목표를 전달할 수 있습니다.

> GOAL
{: .prompt-info }

이 흐름을 하나의 변화로 표현하면 다음과 같습니다.

```
COMMAND
   ↓
PROMPT
   ↓
GOAL
```

전통적인 소프트웨어에서는 사용자가 어떻게 해야 하는지를 컴퓨터에게 알려주었습니다. LLM에서는 사용자가 무엇이 궁금한지를 말합니다. AI Agent에서는 사용자가 무엇을 달성하고 싶은지를 말합니다.

이 변화는 단순한 인터페이스의 변화가 아닙니다. 컴퓨터와 인간이 역할을 나누는 방식 자체가 달라지고 있다는 의미를 가지고 있습니다. 기존에는 사람이 절차를 설계하고 컴퓨터가 그대로 실행했습니다. LLM 시대에는 컴퓨터가 자연어를 이해하고 답변을 생성하기 시작했습니다. 그리고 Agent 시대에는 컴퓨터가 목표를 이해하고 필요한 절차 일부를 스스로 구성해 실행하는 단계로 발전하고 있습니다.

## 요약

LLM과 AI Agent는 서로 밀접하게 연결되어 있지만 역할은 분명히 다릅니다. LLM은 언어를 이해하고 생성하며, 문제를 분석하고 해결 방법을 제안합니다. 반면 AI Agent는 이러한 LLM의 추론 능력에 Tool, Memory, Planning, Execution 기능을 결합하여 실제 목표를 수행합니다.

가장 간단하게 정리하면 다음과 같습니다.

**LLM**

* 무엇을 해야 하는지
* 설명합니다.

**AI Agent**

* 무엇을 해야 하는지 판단하고,
* 필요한 도구를 사용하며,
* 결과를 확인하고,
* 목표를 달성할 때까지
* 작업을 이어갑니다.

> LLM은 정보 생성의 중심이고, AI Agent는 목표 수행의 중심입니다.
{: .prompt-tip }

LLM이 인간과 컴퓨터 사이의 인터페이스를 자연어 중심으로 변화시켰다면, AI Agent는 그 자연어를 실제 행동으로 연결하면서 컴퓨터를 사용하는 방식 자체를 변화시키고 있습니다. 앞으로 AI 시스템을 평가할 때는 단순히 어떤 LLM을 사용하는지만 확인해서는 충분하지 않을 것입니다. 어떤 Tool을 사용할 수 있는지, 어떤 Memory를 가지고 있는지, 어떻게 계획을 세우는지, 어떤 실행 환경에서 동작하는지, 그리고 어떤 권한을 가지고 있는지를 함께 살펴보아야 합니다.

결국 Agent의 실제 능력은 모델 하나가 아니라, 모델과 도구, 기억, 계획, 실행, 권한이 어떻게 하나의 시스템으로 결합되어 있는가​에 의해 결정됩니다.
