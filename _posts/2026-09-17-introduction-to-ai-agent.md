# Introduction to AI Agent

### AI가 '대답하는 존재'에서 '행동하는 존재'로

생성형 AI가 빠르게 발전하면서 **AI Agent(인공지능 에이전트)**라는 개념이 중요하지고 있습니다. 기존의 생성형 AI가 사용자의 질문을 이해하고 적절한 답변을 만들어 내는 데 초점을 두었다면, AI Agent는 한 단계 더 나아가 **사용자가 원하는 목표를 이해하고, 그 목표를 달성하기 위해 필요한 행동을 스스로 선택하고 실행하는 시스템**을 의미합니다.

이를 가장 간단하게 표현하면 다음과 같습니다.

> [!IMPORTANT]
> AI Agent = 목표를 이해하고, 판단하고, 도구를 사용하여 행동하는 AI

여기서 핵심은 **'답변'이 아니라 `행동(Action)'**입니다.

일반적인 챗봇에게 “이 Java 프로그램에서 오류가 발생하는 이유를 찾아줘”라고 요청하면, 챗봇은 제공된 코드와 오류 메시지를 분석하여 해결 방법을 설명합니다. 하지만 AI Agent에게 같은 목표와 필요한 작업 환경을 제공한다면, Agent는 프로젝트 파일을 직접 조사하고, 관련 코드를 검색하고, 오류 로그를 분석하고, 필요한 경우 코드를 수정한 다음 테스트까지 실행할 수 있습니다.

따라서 AI Agent의 등장에는 생성형 AI의 역할이 다음과 같이 확장되고 있다는 의미가 담겨 있습니다.

> [!NOTE]
> Answer → Reason → Plan → Act → Observe → Improve

즉, **_대답하는 AI에서 생각하고 행동하는 AI로의 변화_** 라고 볼 수 있습니다.

### ‘질문’을 받는 것이 아니라 ‘목표’를 받는다

AI Agent를 이해할 때 가장 중요한 개념 중 하나는 **Goal** 입니다.

전통적인 소프트웨어는 사람이 미리 작성한 명령과 절차에 따라 움직입니다. 예를 들어, 프로그램에서 A라는 조건이 발생하면 B를 실행하고, B가 성공하면 C를 실행하도록 개발자가 코드를 작성합니다. 사용자는 사실상 프로그램이 이미 알고 있는 기능 중 하나를 선택합니다.

반면, AI Agent에서는 사용자가 반드시 모든 절차를 지정할 필요가 없습니다. 

사용자는 구체적인 명령의 나열이 없이 아래와 같이 말할 수 있습니다.

> 이 프로젝트의 테스트가 실패하는 원인을 찾아서 수정해 줘.

어떤 파일을 열어야 하는지, 어떤 명령을 실행해야 하는지, 몇 개의 파일을 조사해야 하는지, 코드를 수정해야 하는지, 라이브러리 버전을 변경해야 하는지 사용자는 지정하지 않았습니다. 사용자가 제공한건은 단지 **"목표***입니다.

AI Agent는 이 목표와 현재 환경을 바탕으로 필요한 작업을 결정합니다. 이런 특징 때문에 AI Agent는 흔히 **Goal-oriented system**, 즉 **목표 지향적 시스템**으로 설명할 수 있습니다.

## Agent라는 단어의 의미

'Agent'라는 단어 자체를 의미하면 AI Agent라는 용어도 훨씬 쉽게 이해할 수 있습니다. 영어의 Agent에는 누군가를 대신하여 일을 수행하는 대리인, 행위자라는 의미가 있습니다.

예를 들어 여행사를 통해 항공권과 호텔을 예약할 때, 사용자는 여행사 직원에게 모든 클릭 순서를 지시하지 않습니다.

> "다음 주에 도쿄에 가려고 합니다. 조건에 맞는 일정을 알아봐 주세요."

라고 목표와 조건을 전달합니다. 그러면 담당자는 필요한 정보를 조사하고, 여러 선택지를 비교하고, 추가 정보가 필요하면 사용자에게 질문하며, 최종적으로 사용자가 원하는 결과를 얻을 수 있도록 일을 수행합니다.

AI Agent에서 Agent라는 표현을 사용하는 이유도 이와 비슷합니다.

> [!IMPORTANT]
> 사용자를 대신하여 목표 달성에 필요한 작업을 수행하는 AI

라는 의미가 담겨 있습니다.

다만 중요한 차이가 있습니다. AI Agent가 완전히 독립적으로 모든 일을 결정해야 하는 것은 아닙니다. 실제 시스템에서는 중요한 행동을 수행하기 전에 사용자의 승인을 받도록 설계하는 경우가 많습니다.

따라서 Agent의 **자율성(Autonomy)**은 ‘있다/없다’의 이분법보다는 **어느 정도까지 스스로 행동하도록 허용했는가**의 문제에 가깝습니다.

## AI Agent와 AI 모델

AI Agent를 처음 접할 때 하는 가장 큰 오해는 **AI Agent = LLM**이라고 생각하는 것입니다. 한마디로 이야기하면 둘은 다릅니다.

GPT와 같은 Large Language Model(LLM)은 Agent의 중요한 구성 요소가 될 수 있지만, LLM 하나만으로 완전한 Agent가 만들어지는 것은 아닙니다.

이를 사람에 비유하면 이해하기 쉽습니다.

> [!IMPORTANT]
> LLM은 ‘두뇌’에 가깝고, AI Agent는 ‘행동할 수 있는 전체 시스템’에 가깝습니다.

Agent에는 LLM 외에도 여러 구성 요소가 필요합니다.

LLM
: 생각하고 판단한다.

Context
: 현재 상황과 작업에 필요한 정보를 제공한다.

Memory
: 과거의 정보와 경험을 저장하고 필요할 때 다시 활용한다.

Planning
: 목표를 여러 개의 작은 작업으로 나눈다.

Tools
: 파일, 터미널, 브라우저, 데이터베이스, API 등을 사용한다.

Skills
: 특정 작업을 수행하는 방법을 재사용한다.

Execution Environment
: 실제 명령과 프로그램이 실행되는 환경을 제공한다.

Observation
: 실행 결과를 확인한다.

Orchestration
: 이 모든 구성 요소의 실행 순서와 상태를 관리한다.

따라서 전체적인 관계는 다음과 같이 생각할 수 있습니다.

```
                         AI AGENT
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
         LLM              Memory            Tools
     "어떻게 할까?"      "무엇을 알지?"     "무엇을 할까?"
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ▼
                         Planning
                    "어떤 순서로 할까?"
                            │
                            ▼
                         Execution
                       "실제로 실행"
                            │
                            ▼
                        Observation
                     "결과가 어떻게 됐지?"
                            │
                            ▼
                        Evaluation
                     "목표를 달성했나?"
```

즉, **LLM이 Agent의 추론 엔진이라면 Agent 소프트웨어는 그 추론을 실제 행동으로 연결하는 시스템**입니다.

## AI Agent의 핵심: '판단과 행동의 반복'

AI Agent를 이해하는 가장 중요한 구조는 Agent Loop입니다.

Agent는 한 번 생각하고 한 번 실행한 뒤 끝나는 것이 아니라, 실행 결과를 다시 관찰하고 다음 행동을 결정할 수 있습니다.

이를 간단히 표현하면 다음과 같습니다.

> **THINK → ACT → OBSERVE → THINK → ACT → OBSERVE**

조금 더 구체적으로 표현하면,

```
목표 이해
    ↓
현재 상황 파악
    ↓
다음 행동 결정
    ↓
도구 실행
    ↓
결과 관찰
    ↓
목표 달성 여부 판단
    ↓
필요하면 계획 수정
    ↓
다시 행동
```

이라는 순환 구조가 만들어집니다.

예를 들어 Agent가 Java 프로그램을 수정하고 있다고 하겠습니다.

처음에는 mvn test를 실행합니다. 테스트가 실패합니다. Agent는 실패했다는 사실만 보고 멈추는 것이 아니라 오류 메시지를 새로운 정보로 받아들입니다.

```
NullPointerException at StudentService.java:84
```

이 결과가 Agent의 Observation이 됩니다. Agent는 다시 판단합니다. "StudentService.java의 84번째 줄과 관련된 객체의 초기화 과정을 확인해야 한다." 그리고 파일 검색이나 읽기 도구를 실행합니다.

코드를 분석한 후 수정하고 다시 테스트합니다. 이번에는 다른 테스트가 실패할 수도 있습니다. 그러면 Agent는 다시 오류를 관찰하고 다음 행동을 결정합니다. 결국 다음과 같은 순환이 형성됩니다.

> 생각한다. → 행동한다. → 결과를 본다. → 결과를 바탕으로 다시 생각한다.

이 반복 구조 때문에 Agent는 고정된 스크립트보다 훨씬 유연하게 문제를 처리할 수 있습니다.

## AI Agent와 기존 자동화 프로그램의 차이점

전통적인 자동화 프로그램 역시 사람 대신 일을 합니다.

예를 들어 매일 오전 9시에 데이터베이스에서 매출 데이터를 가져와 CSV 파일을 만들고 이메일로 전송하는 프로그램을 생각해 볼 수 있습니다. 이 프로그램의 흐름은 개발자가 미리 정의합니다.

> 09:00 → DB 조회 → CSV 생성 → 이메일 전송

이를 Workflow Automation이라고 볼 수 있습니다. 문제는 예상하지 못한 상황이 발생했을 때입니다.

데이터베이스 연결에 실패하거나 데이터 형식이 변경되었다면 기존 프로그램은 미리 작성된 예외 처리 범위를 넘어서는 상황에서 작업을 중단할 가능성이 높습니다.

AI Agent는 상황을 해석하여 다음 행동을 결정할 여지가 있습니다

```
DB 연결 실패
    ↓
"일시적인 네트워크 문제인가?"
    ↓
재시도
    ↓
여전히 실패
    ↓
"인증 정보 또는 서버 상태를 확인해야 하는가?"
    ↓
관련 로그 확인
    ↓
문제 분석
    ↓
필요하면 사용자에게 보고
```

즉, 기존 자동화가

> "정해진 절차를 자동으로 실행한다.

에 가깝다면 AI Agent는

> "주어진 목표를 달성하기 위해 상황에 따라 절차를 선택한다."

에 더 가깝습니다.

물론 실제로는 둘을 결합하는 것이 일반적입니다. 예측 가능한 부분은 전통적인 workflow로 처리하고, 판단이 필요한 부분에만 AI Agent를 사용하는 방식이 안정성·비용·통제 측면에서 유리할 수 있습니다.

## 도구를 사용할 수 있다!

AI Agent의 능력을 결정하는 중요한 요소 중 하나가 Tool Use입니다.

LLM에게 아무리 뛰어난 추론 능력이 있어도 외부 세계와 연결되어 있지 않으면 할 수 있는 일은 제한적입니다. 예를 들어 LLM은

> "프로젝트에서 StudentRepository라는 문자열을 검색하세요."

라고 알려줄 수 있습니다.

하지만 파일 검색 Tool이 연결된 Agent라면 직접 검색할 수 있습니다.

```
rg "StudentRepository" .
```

검색 결과를 받은 Agent는 다시 해당 파일을 읽고 분석할 수 있습니다. 따라서 Tool은 AI에게 일종의 손과 발을 제공한다고 볼 수 있습니다.

Agent가 연결할 수 있는 도구에는 다음과 같은 것들이 있습니다.

* File System — 파일 읽기·쓰기·검색
* Shell — PowerShell, Bash 등의 명령 실행
* Browser — 웹페이지 탐색 및 조작
* Search — 인터넷 정보 검색
* Git — 소스 버전 관리
* GitHub — Issue, Pull Request, Repository 작업
* Database — SQL 실행 및 데이터 조회
* Python — 데이터 처리와 계산
* API — 외부 서비스 사용
* Email / Calendar — 업무 시스템과 상호작용

그래서 같은 LLM을 사용하더라도 어떤 Tool과 권한을 제공했는가에 따라 Agent의 능력은 크게 달라질 수 있습니다.

## AI Agent의 자율성

AI Agent를 설명할 때 **Autonomous**, 즉 '자율적'이라는 표현이 자주 등장합니다. 

하지만 이것을 인간처럼 완전히 독립적으로 행동한다는 의미로 이해하면 정확하지 않습니다. Agent의 자율성은 단계적으로 생각하는 것이 좋습니다.

1. Level 1 - Assistant  
사용자가 요청하면 방법을 알려줍니다.  
**"이 명령을 실행하세요"**
2. Level 2 - Tool-using Assistant  
사용자의 요청에 따라 도구를 직접 실행합니다.  
**"제가 검색해 보겠습니다"**
3. Level 3 - Agent  
목표를 받고 필요한 작업을 여러 단계로 수행한다.  
**"먼저 프로젝트를 조사하고, 테스트를 실행한 뒤 오류를 분석하겠습니다."**
4. Level 4 — Autonomous Agent  
상대적으로 장기간 목표를 유지하면서 상황에 따라 계획을 수정하고 여러 작업을 수행한다.
**"Goal → Plan → Execute → Observe → Replan → Execute"**

따라서 Agent 시스템을 설계할 때 중요한 질문은

> "AI에게 얼마나 많은 자율성을 줄 것인가?"

입니다.


## 자율성과 안전장치

Agent에게 파일 읽기만 허용하는 것과 서버 배포 권한까지 제공하는 것은 완전히 다른 문제입니다.

예를 들어 다음과 같은 권한을 가진 Agent를 생각해 보겠습니다.

* Read File ✓
* Write File ✓
* Delete File ✓
* Shell ✓
* Git Push ✓
* Database Write ✓
* Cloud Deployment ✓
* Email Send ✓

이 정도의 권한을 가진 Agent는 매우 유용하지만, 잘못된 판단의 영향 역시 커집니다. 따라서 실제 Agent 시스템에서는 Human-in-the-loop가 중요합니다. 즉,

> [!IMPORTANT]
> AI가 판단하되 중요한 결정은 사람이 승인한다.

예를 들어 검색이나 테스트 실행은 자동으로 허용하면서 다음과 같은 작업에서는 사용자 승인을 요구할 수 있습니다.

* 파일 대량 삭제
* 데이터베이스 데이터 변경
* git push
* Production 배포
* 외부 이메일 발송
* 구매 또는 결제

좋은 AI Agent란 단순히 "가장 자율적으로 움직이는 Agent"가 아니라, 목적에 맞는 자율성과 통제 장치를 갖춘 Agent라고 보는 편이 정확합니다.

## AI Agent의 본질

지금까지의 내용을 하나의 흐름으로 압축하면 AI Agent의 본질이 명확해집니다.

GOAL
: 무엇을 달성해야 하는가?

↓

PERCEIVE
: 현재 상황은 어떠한가?

↓

REASON
: 무엇을 해야 하는가?

↓

PLAN
: 어떤 순서로 해야 하는가?

↓

ACT
: 도구를 사용하여 행동한다.

↓

OBSERVE
: 행동의 결과를 확인한다.

↓

EVALUATE
: 목표를 달성했는가?

↓

**NO → REPLAN → ACT → OBSERVE**

이것이 AI Agent를 이해하는 가장 중요한 구조입니다. 

AI Agent는 단순히 "질문에 대답하는 똑똑한 프로그램"이 아닙니다. AI Agent는 주어진 목표와 현재 환경을 이해하고, 필요한 행동을 계획하며, 외부 도구를 사용해 실제 작업을 수행하고, 그 결과를 관찰하여 다음 행동을 결정하는 목표 지향적 AI 시스템입니다.

그리고 바로 이 지점에서 생성형 AI의 역할이 크게 변화합니다.

> Chat AI: "무엇을 알려줄까?" 에서 
> Agentic AI: "목표를 달성하려면 무엇을 해야 할까?" 로 변화하는 것입니다.

따라서 AI Agent의 발전은 단순히 더 좋은 챗봇의 등장이라기보다, AI가 Answer Generator에서 Task Executor로 확장되는 과정으로 이해하는 것이 핵심입니다.
